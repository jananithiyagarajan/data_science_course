## 1. Views

A **View** is a virtual table based on the result of a SELECT query.
Views do not store data; they are re-executed every time they are queried.

```sql
-- Create a view
CREATE VIEW high_earners AS
SELECT emp_name, department, salary
FROM employees
WHERE salary > 50000;

-- Query the view like a table
SELECT * FROM high_earners;

-- Update a view
CREATE OR REPLACE VIEW high_earners AS
SELECT emp_name, department, salary, city
FROM employees
WHERE salary > 50000;

-- Drop a view
DROP VIEW high_earners;
```

### Benefits of Views
- Simplify complex queries
- Provide security by hiding columns
- Create consistent interfaces for applications

## 2. Stored Procedures

A **Stored Procedure** is a prepared SQL code block saved in the database that you can reuse by calling it.

### Creating a Stored Procedure

```sql
DELIMITER //

CREATE PROCEDURE GetEmployeesByDept(IN dept_name VARCHAR(50))
BEGIN
    SELECT emp_name, salary
    FROM employees
    WHERE department = dept_name;
END //

DELIMITER ;

-- Call the procedure
CALL GetEmployeesByDept('IT');
```

### Procedure with OUT parameter

```sql
DELIMITER //

CREATE PROCEDURE GetAvgSalary(IN dept_name VARCHAR(50), OUT avg_sal DECIMAL(10,2))
BEGIN
    SELECT AVG(salary) INTO avg_sal
    FROM employees
    WHERE department = dept_name;
END //

DELIMITER ;

-- Call and get result
CALL GetAvgSalary('IT', @result);
SELECT @result AS average_salary;
```

### Procedure with IF-ELSE Logic

```sql
DELIMITER //

CREATE PROCEDURE GiveRaise(IN emp_id INT, IN pct DECIMAL(5,2))
BEGIN
    IF pct > 50 THEN
        SIGNAL SQLSTATE '45000'
        SET MESSAGE_TEXT = 'Raise percentage too high!';
    ELSE
        UPDATE employees
        SET salary = salary * (1 + pct/100)
        WHERE emp_id = emp_id;
        SELECT 'Raise applied successfully' AS result;
    END IF;
END //

DELIMITER ;
```

### Drop a Procedure

```sql
DROP PROCEDURE IF EXISTS GetEmployeesByDept;
```

## 3. User-Defined Functions (UDFs)

A **Function** returns a single value and can be used in SELECT statements.
Unlike procedures, functions cannot modify data.

```sql
DELIMITER //

CREATE FUNCTION GetAnnualSalary(monthly_salary DECIMAL(10,2))
RETURNS DECIMAL(12,2)
DETERMINISTIC
BEGIN
    RETURN monthly_salary * 12;
END //

DELIMITER ;

-- Use in a query
SELECT emp_name, salary,
       GetAnnualSalary(salary) AS annual_salary
FROM employees;
```

### Another Example: Grade Function

```sql
DELIMITER //

CREATE FUNCTION GetGrade(score INT)
RETURNS VARCHAR(5)
DETERMINISTIC
BEGIN
    DECLARE grade VARCHAR(5);
    IF score >= 90 THEN SET grade = 'A+';
    ELSEIF score >= 75 THEN SET grade = 'A';
    ELSEIF score >= 60 THEN SET grade = 'B';
    ELSEIF score >= 45 THEN SET grade = 'C';
    ELSE SET grade = 'F';
    END IF;
    RETURN grade;
END //

DELIMITER ;

-- Use it
SELECT student_name, score, GetGrade(score) AS grade
FROM students;
```

### Stored Procedure vs Function

| Feature         | Stored Procedure        | Function               |
| --------------- | ----------------------- | ---------------------- |
| Returns         | 0 or more values        | Exactly 1 value        |
| Use in SELECT   | ❌ Cannot                | ✅ Can                  |
| Can modify data | ✅ Yes                   | ❌ No (typically)       |
| Called with     | `CALL`                  | Used as expression     |

## 4. Triggers

A **Trigger** automatically executes a SQL block in response to an INSERT, UPDATE, or DELETE event.

```sql
-- Trigger: log every salary update
CREATE TABLE salary_audit (
    audit_id INT AUTO_INCREMENT PRIMARY KEY,
    emp_id INT,
    old_salary DECIMAL(10,2),
    new_salary DECIMAL(10,2),
    changed_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

DELIMITER //

CREATE TRIGGER log_salary_change
AFTER UPDATE ON employees
FOR EACH ROW
BEGIN
    IF OLD.salary <> NEW.salary THEN
        INSERT INTO salary_audit (emp_id, old_salary, new_salary)
        VALUES (OLD.emp_id, OLD.salary, NEW.salary);
    END IF;
END //

DELIMITER ;

-- Test it
UPDATE employees SET salary = 70000 WHERE emp_id = 1;
SELECT * FROM salary_audit;
```

### Trigger Types

| Timing  | Event    | Full Name                 |
| ------- | -------- | ------------------------- |
| BEFORE  | INSERT   | BEFORE INSERT             |
| AFTER   | INSERT   | AFTER INSERT              |
| BEFORE  | UPDATE   | BEFORE UPDATE             |
| AFTER   | UPDATE   | AFTER UPDATE              |
| BEFORE  | DELETE   | BEFORE DELETE             |
| AFTER   | DELETE   | AFTER DELETE              |

## 5. ACID Properties

**ACID** properties guarantee database transactions are processed reliably.

| Property        | Meaning                                                        |
| --------------- | -------------------------------------------------------------- |
| **A**tomicity   | All operations in a transaction succeed or all are rolled back |
| **C**onsistency | Data remains in a valid state before and after the transaction |
| **I**solation   | Concurrent transactions don't interfere with each other        |
| **D**urability  | Committed data is permanently saved, even after system failure |

### Example: Bank Transfer (ACID in action)

```sql
START TRANSACTION;

-- Deduct from Account A
UPDATE accounts SET balance = balance - 5000 WHERE account_id = 'A001';

-- Add to Account B
UPDATE accounts SET balance = balance + 5000 WHERE account_id = 'B002';

-- If both succeed → COMMIT
COMMIT;

-- If anything fails → ROLLBACK
ROLLBACK;
```

Without ACID: if the server crashes after deducting from A but before adding to B, money disappears!

## 6. Common Table Expressions (CTEs)

A **CTE** (WITH clause) is a temporary named result set that you define at the top of a query.
It makes complex queries more readable and reusable within the same statement.

### Basic CTE Syntax

```sql
WITH cte_name AS (
    SELECT ...
    FROM ...
    WHERE ...
)
SELECT * FROM cte_name;
```

### Example 1: Simple CTE

```sql
WITH high_earners AS (
    SELECT emp_name, department, salary
    FROM employees
    WHERE salary > 50000
)
SELECT department, COUNT(*) AS count
FROM high_earners
GROUP BY department;
```

### Example 2: Multiple CTEs

```sql
WITH
it_dept AS (
    SELECT emp_name, salary FROM employees WHERE department = 'IT'
),
hr_dept AS (
    SELECT emp_name, salary FROM employees WHERE department = 'HR'
)
SELECT 'IT' AS dept, emp_name, salary FROM it_dept
UNION ALL
SELECT 'HR', emp_name, salary FROM hr_dept;
```

### Example 3: Recursive CTE (Employee Hierarchy)

```sql
-- Table with manager_id
CREATE TABLE org (
    emp_id INT, emp_name VARCHAR(50), manager_id INT
);

INSERT INTO org VALUES
(1, 'CEO', NULL),
(2, 'VP Sales', 1),
(3, 'VP Tech', 1),
(4, 'Manager A', 2),
(5, 'Manager B', 3),
(6, 'Engineer', 5);

-- Recursive CTE to build the hierarchy
WITH RECURSIVE org_hierarchy AS (
    -- Anchor: start with CEO
    SELECT emp_id, emp_name, manager_id, 1 AS level
    FROM org
    WHERE manager_id IS NULL

    UNION ALL

    -- Recursive: find each employee's reports
    SELECT e.emp_id, e.emp_name, e.manager_id, oh.level + 1
    FROM org e
    INNER JOIN org_hierarchy oh ON e.manager_id = oh.emp_id
)
SELECT * FROM org_hierarchy ORDER BY level;
```

### CTE vs Subquery

| Feature         | Subquery              | CTE                        |
| --------------- | --------------------- | -------------------------- |
| Readability     | Can be hard to read   | Much more readable         |
| Reusability     | Must repeat           | Can reference multiple times|
| Recursion       | ❌ Not supported       | ✅ Supported                |
| Performance     | Similar               | Similar (optimizer decides)|
